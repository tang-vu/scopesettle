# Independent verifier SDK and CLI

ScopeSettle ships a verifier that reads X Layer directly. It does not call the ScopeSettle web API
and does not trust a verification certificate previously generated by the application. Given the
canonical report, funded specification, deployment addresses, and an RPC endpoint, it rebuilds all
ten verification checks locally.

## Command-line verification

Build the workspace package, then run the CLI against a supported X Layer deployment:

```powershell
pnpm --filter @scopesettle/sdk build
pnpm --filter @scopesettle/sdk cli -- `
  --chain-id 1952 `
  --rpc-url https://testrpc.xlayer.tech `
  --commerce <commerce-contract> `
  --evaluator <evaluator-contract> `
  --job-id <job-id> `
  --report .\report.json `
  --specification .\specification.json
```

Add `--json` for canonical, machine-readable output. Exit code `0` means every check passed, `2`
means no check failed but required public context was unavailable, and `1` means verification or
input validation failed. Automation must inspect the exit code or `verification.status`; the
presence of a certificate alone is not success.

The CLI validates both input files with the canonical Zod schemas, limits each file to 2 MiB, and
rejects unknown or repeated options. It never executes deliverable code.

## TypeScript integration

```ts
import { createScopeSettleVerifier } from "@scopesettle/sdk";

const verifier = createScopeSettleVerifier({
  chainId: 1952,
  rpcUrl: process.env.XLAYER_RPC_URL!,
  commerceAddress: "0x...",
  evaluatorAddress: "0x...",
});

const certificate = await verifier.verifyJob({
  jobId: 3n,
  report,
  specification,
});

if (certificate.verification.status !== "verified") {
  throw new Error("The report is not fully bound to public onchain state");
}
```

Applications should validate or construct `report` and `specification` with the schemas exported by
`@scopesettle/shared` before calling the SDK. The verifier normalizes contract addresses and rejects
unsupported chain IDs at configuration time.

## Trust and operations

- Treat the RPC response, report, and specification as untrusted inputs. Use an independently
  operated RPC provider for high-value decisions.
- The supplied commerce and evaluator addresses are explicit security parameters. Obtain them from
  a checked deployment record; never infer or invent an address.
- An RPC URL can contain credentials. Keep it in an environment variable and do not include it in
  logs, issue reports, or verification artifacts.
- `generatedAt` records when the read occurred. It is not part of the proof and will vary between
  runs; the checks and their observed/expected commitments are the reproducible result.
- A fully verified certificate proves consistency and binding, not correctness of the trusted AI
  evaluator's judgment or contract security.

The exact check definitions and aggregate-state rules are specified in the
[verification protocol](verification.md).
